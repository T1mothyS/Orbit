# Next

- 中期版上线后的顺序：先修复真实使用与下一次自然定时暴露的阻断问题；再实现跨日事件记忆和可审计的人工纠正；最后按独立任务卡推进其余终极目标。保留七个不同日期 Shadow、OAuth 续用、收件箱和媒体下架等未完成技术验收，但不倒写为本次上线前置。
- 在明确授权且准备好隔离/生产证据后，观察至少三次日报实际运行、至少两个日期，并单独记录 notification、queue、SMTP accepted、provider feedback 和 inbox arrival。
- 继续按现有本地预构建、备份、原子切换、health/静态资源和回滚规则做生产发布，并分层记录邮件内容、SMTP 接受和收件箱到达证据。
- 根据真实搜索数据量和响应时间再决定是否增加索引；当前 AI 检索保持词法匹配，不引入向量库、Embedding、RAG 或外部搜索服务。
- CalDAV 全量单向与设置页已本地实现：预览/确认、问题项、迁移、受控自动化和恢复保护；后续按 [桥接合同](CALDAV-BRIDGE.md) 完成生产扩大范围、手机核心验收、24h观察与提醒单独放行，不把本地完成当作生产上线。
- 日历与历史数据兼容：将“个人/工作/家庭”等真实日历选择与“出行/工作/社交/生活/健康/其他”分类筛选分开呈现；为旧版全天事件和多日全天事件定义可复核的结束日期语义，先提供修复预览/迁移，再允许桥接。

# Later

Daily Digest 后续功能阶段按中期版的实际使用结果再收紧设计；本轮上线与交接后不自动启动下一张功能卡：

| 阶段 | 目标与验收 | 难度与主要风险 |
|---|---|---|
| V3 Core | Event、Revision、Evidence、Analysis；`intelligence.read_inputs`/`submit_analysis`；匹配建议、可纠正合并、版本引用；至少 30 个固定真实案例及连续 Shadow 正确区分重复、不同事件、后续进展、无变化 | 高；错误合并、转载伪装成独立证据、历史漂移、数据增长 |
| Scheduled Events 与 Macro | Exact/Window、首批中美宏观和财报，实际/前值/修订/预期及来源分开保存；检查 Playbook；验收时区、夏令时、延期取消、延迟、缺预期和修订 | 中高；来源结构变化、周期/单位混淆、时间不可靠 |
| Research、Thesis、Radar、Flash | 研究历史；用户确认的 Thesis/Proposal；低频候选；先验证服务器触发 Agent，不满足则定时领取；订阅、核实、实质变化、去重与上限全部满足后提醒 | 高；误报、重复提醒、触发权限、成本与状态增长 |

每个 Release 报告已完成/未完成、分层证据、Git/版本/文档、剩余风险、下一目标及更新后的难度。七日观察与自然定时继续独立记录，不提前宣称 V3 Core 已上线。

## Daily Digest 小步交付清单（2026-09-22 规划）

这是一份后续任务拆分，不是第二至第四阶段的实施授权。第一阶段整体验收完成后，再按编号授权；正式切换、真实发信和 push 仍分别处理。各任务结果和准确暂停位置追加本机连续记录，本表保持范围与依赖的主要来源。

### 适合有限额度的节奏

- 一次只执行一个编号，不把整个阶段塞进一次会话。不按模型套餐承诺固定开发小时或任务数；额度随模型、上下文和工具使用变化。
- S：单一规则、查询、合同或证据审计；M：一个数据行为或一个界面。M 是单次任务上限；若同时需要迁移、UI、部署或两个外部来源，先拆成 a/b 子任务。
- 每次先读交接和实际 diff，明确交付物及验收；完成后先验证、更新必要文档/版本并建立本地 commit，再考虑新任务。不要把额度耗尽前的最后一步安排为部署或迁移。
- 节奏默认每轮一个开发卡；每完成两到三个开发卡安排一次整合/复核卡，优先修复已发现的问题。外部服务或长期观察独立安排，不靠长时间保持会话等结果。
- 预留约四分之一的工作范围给测试、修复和交接；这只是计划余量，不是可测的额度保证。遇到需求扩张、第二个未知外部依赖或反复失败，停止扩大范围，写清阻塞和下一条最小验证。
- 已完成代码卡执行项目规定的 typecheck、test、build、diff 检查；UI 卡另验四尺寸。过程中先跑相关测试；完整检查因额度未完成时，标记待验收，不伪报通过，也不将实验 WIP 标记完成。
- 文档/证据卡无应用行为变化时不升应用版本，不重复无关全量测试；代码逻辑交付按现有版本规则更新。一个卡可形成一个完整本地提交；阶段 Release 在整合验收后形成，不把每张卡当作生产发布。
- 推荐续做指令：`执行 S2-03；先读连续记录和 Git diff，只完成这张卡及必要验证，完成后交接，不自动开始下一张。`

交接固定保留：任务编号/状态、基线与当前版本/commit、已改文件与行为、执行过的测试、未完成验证、阻塞、下一条具体操作、外部副作用。失败或额度结束时保留有效修改，不为清理工作区丢弃 WIP。

### 排期与调整

第二阶段13张、第三阶段11张、第四阶段13张，共37张后续卡，另有第一阶段收口卡。卡数不等于额度窗口数：外部验收可能跨日，M卡可能继续拆分，失败修复可新增有明确范围的卡。不要据此承诺37个窗口必定完成。

第一批建议顺序为第一阶段收口 → S2-01 → S2-02 → S2-03；完成S2-07后用实际消耗重估后续卡大小。可以每个可用窗口完成一张S卡或一张已收紧的M卡，余量不足只复核/交接；无需每天强制更新应用。

- 文章收藏、附件和更完整的版本 diff。

# Ideas

- AI 辅助整理为草稿，必须用户确认后保存。
- 更精确的知识来源引用、段落级摘要和跨项目阅读入口。
- 有实际数据证明普通搜索不足后，再评估 embedding、hybrid search、reranker 和 RAG。

# Won't Do

- Google Docs 式实时协作、CRDT 和多人实时编辑。
- 本地 Markdown 与服务器正文双向同步。
- NoteBoard 或 Daily Report 自动单向生成 Knowledge Fragment；两者继续在各自本地流程维护并上传到各自目标系统。
- 向量数据库、RAG 或自动 AI 覆盖原知识，直到普通知识库稳定且有真实使用需求。
- 自动网页抓取、浏览器插件、复杂富文本编辑器、公共知识社区和无限层级文件夹。
- 为了形式一次性重写整个 server/index.ts 或建立复杂全文搜索服务。
